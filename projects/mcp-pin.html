mcp-pin. A lock file for MCP tool definitions.

MCP servers give an AI agent tools, and the model reads each tool’s description as instructions. A server you approved can change that description later. mcp-pin fails CI when a tool definition changes and scans descriptions for the common shapes of hidden prompt injection.

0.18%

false alarms on 3,288 description strings pulled from the source of five servers it had never seen: 6 flagged, none an attack. A rough figure: 4 of the 6 were not tool descriptions.

Limit: the scan is a list of regexes, tuned on the 12 poisoned examples it catches; its catch rate on unseen attacks is unmeasured. The lock file is the stronger control.

1 tools, 1 changes
$ POISON=1 mcp-pin scan -- python tests/fixture_server.py
add: hidden-tag: "<IMPORTANT" -- a tag like <IMPORTANT> marks text as orders for the model; users rarely read it
add: other-tool: "Before using this tool" -- gives orders about when or how a tool is called; can shadow another tool
add: sensitive-path: "~/.cursor" -- names a file that holds keys, credentials or MCP config
1 tools, 3 findings

A changed tool description, caught in CI

Situation

An agent can run tools from third-party MCP servers. Clients show a tool’s description at install time, not on every update, so a description rewritten later goes unread.

Obstacle

Pattern scanning alone is easy to write around, and a scanner that flags ordinary descriptions gets switched off. It had to run in CI with no account, no network calls of its own and no API key.

Action

lock saves a fingerprint (SHA-256) of each tool’s name, description, inputs and annotations. check fails the build if any fingerprint changes, until a person re-locks. scan flags nine shapes, from <IMPORTANT> tags to invisible characters.

Result

6 of 3,288 descriptions flagged on the unseen test set, all false alarms. A finding exits 1 and a broken setup exits 2, so CI can tell the two apart.

Constraints: one Python file, two dependencies (mcp, anyio), offline, stdio servers only, English-only patterns.

The lock is the control, the scan a second look

The decision

Any changed definition fails the check, whatever the change says, because only a person can judge it. The scan runs beside the lock, not in its place, and the README says plainly that a clean scan does not make a server safe.

What was dropped

The first held-out set stopped being held out: one pattern was narrowed after looking at its alarms. So five new server repositories were named before download, no pattern changed, and they were scanned once, at the end. That run is the 0.18%.

.github / workflows / mcp-pin.yml
name: mcp-pin
on: [push, pull_request]
jobs:
  mcp-pin:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements.txt
      - uses: yiklin22/mcp-pin@main
        with:
          server: python server.py
          python-version: ""
      - uses: yiklin22/mcp-pin@main
        with:
          command: scan
          server: python server.py
          python-version: ""

Run mcp-pin yourself

Python and the command that starts your server over stdio. Lock it locally, commit mcp-lock.json, then run check in CI. Set a job timeout: a server that starts but never answers hangs the run.

Where the figure comes from

docs/measurements.md, which lists every repository and commit scanned, from scripts/scan_sources.py.
