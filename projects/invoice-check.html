invoice-check. Invoices against their orders.

Accounts payable checks every invoice against its order before paying. invoice-check reads supplier PDFs, compares them line by line with a purchase-order CSV, and shows each disagreement next to the place on the page where the value was read.

20 of 20

test invoices, each built with a known condition, came out with exactly that finding and nothing extra: 7 clean, the rest each with a planted problem.

Limit: the 20 invoices are synthetic text PDFs from three invented suppliers, read by templates written for them. No real invoice and no real user has been through it.

Every line against its order

Situation

A wrong invoice paid is money gone: a price above the order, a quantity billed twice, the same invoice under a new number. Checking by hand means reading every line of every invoice.

Obstacle

A fuzzy match turns a wrong guess into a silently approved payment. Amounts must stay exact to the cent, and one account must never see another’s invoices.

Action

Exact matching only, with money parsed from the printed characters into Decimal. Each account is checked twice, in the web layer and in the service, and 132 tests run on a real PostgreSQL.

Result

All 20 seeded conditions surfaced as seeded, with nothing extra, and uploading the same 20 files again added no records. A second account asking for the first one’s files was refused.

Constraints: one machine, synthetic fixtures, no hosted deployment, and an optional model step (Claude, off by default) that has read only fixture invoices.

A near match never passes an invoice

The decision

Orders and SKUs match exactly or not at all. “PO 1007” for PO-1007 is reported with its candidate and waits for a person. “Unreadable” is a state with a reason, never an empty invoice, and an unreadable file cannot be approved.

What was dropped

Fuzzy matching with a score was rejected. Model extraction was held back too: three hand-written templates read all 144 values of the 18 readable fixtures, so the model step came later, off by default, and it never marks an invoice clean on its own.

Run invoice-check yourself

uv, and nothing else to install: without DATABASE_URL the app starts its own PostgreSQL. The demo script drives a running server through the whole flow with two throwaway accounts and deletes them at the end.

Where the figure comes from

docs/demo-run.txt, the output of scripts/demo.py against a running server, account checks included.

Read the README and the full results

invoice-check / terminal
$ uv sync
$ uv run uvicorn invoicecheck.app:app --port 8811  # open http://127.0.0.1:8811 and create an account
$ uv run python scripts/demo.py http://127.0.0.1:8811  # two throwaway accounts, deleted at the end
$ uv run pytest  # 132 tests, on a real PostgreSQL
