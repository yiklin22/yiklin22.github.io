Marley。Claude 和 ChatGPT，由店主放行。

Marley 是一個團隊產品，讀取餐廳的供應商發票，並追蹤每個品項的價格變化。我負責的部分，是讓 Claude、ChatGPT 和其他 MCP 用戶端，在店主登入並以 OAuth 2.1 允許該應用程式之後，透過六個唯讀工具讀取這家餐廳的價格。

73 / 73

項登入流程與 /mcp 的測試全數通過，包括：重複使用授權碼或更新權杖會撤銷整個授權、錯誤的 PKCE 驗證碼會被拒絕，以及權杖只能讀取允許它的那家餐廳。

限制：這項工作還在一個私人儲存庫的分支上，尚未合併或上線，也還沒有任何店主連接過應用程式。

一家餐廳的價格，只讓店主允許的應用程式讀取

情境

店主已經會問 Claude 或 ChatGPT 關於自家生意的問題，但發票和價格都在 Marley 裡。MCP 端點讓這些應用程式直接讀取，店主不必再手動把數字複製過去。

阻礙

支出資料是私密的，而任何應用程式都能用任何名稱自行註冊。每個應用程式都必須經過餐廳店主允許、只能看到那家餐廳，而且店主一中斷連線就立刻失去存取權。

行動

在 MCP SDK 的處理器上實作 OAuth 2.1：動態註冊只接受 https 重新導向、強制使用 PKCE S256、資源固定為本伺服器的 /mcp，以及一組五分鐘內有效的一次性授權碼，綁定用戶端、重新導向網址、PKCE 挑戰值與餐廳。

結果

73 項測試通過。授權碼、權杖與用戶端密鑰都以雜湊儲存，更新權杖每次使用都會輪替，店主可以在「帳戶」中查看並中斷應用程式的連線。另一次審查在這個分支上找到的問題，都已在同一分支修正並加上測試。

條件限制：FastAPI 與 MCP Python SDK、沿用既有的電子郵件驗證碼登入、訪客工作階段絕不能連接應用程式，而且未設定 PUBLIC_URL 時全部關閉。

同意在 Marley 上進行，而且在發出請求的那個瀏覽器

決策

授權步驟會把瀏覽器導向 Marley 的連接畫面，只有擁有帳號的店主能在那裡以電子郵件驗證碼登入並點選「允許」；訪客永遠不行。授權時設定的 cookie 會把請求綁定到該瀏覽器，而「允許」會指名畫面上顯示的那家餐廳，所以如果瀏覽器之後改登入另一家餐廳，就會被再問一次。

它拒絕什麼

任何會寫入的工具：這六個工具都是 Marley 自家聊天功能所用的唯讀工具。錯誤只會導回已知的 Claude 與 ChatGPT 回呼網址；其他應用程式的錯誤則留在 Marley 上顯示，而且當應用程式的重新導向主機不是 claude.ai 或 chatgpt.com 時，同意畫面會發出警告。
