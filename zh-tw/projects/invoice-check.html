invoice-check。拿發票對照訂單。

應付帳款部門在付款前，會拿每張發票對照它的訂單。invoice-check 讀取供應商的 PDF，逐行與採購單 CSV 比對，並把每一處不一致標示在頁面上讀到該值的位置旁。

20 / 20

份測試發票各自依已知狀況建立，結果都恰好得出該狀況、沒有多餘的發現：7 份無異常，其餘每份各埋了一個問題。

限制：這 20 份發票是來自三家虛構供應商的合成文字 PDF，並由專為它們撰寫的範本讀取。還沒有真實發票或真實使用者用過它。

每一行都對照它的訂單

情境

付錯一張發票，錢就沒了：價格高於訂單、同一數量被請款兩次、同一張發票換了新號碼。人工檢查意味著要讀完每張發票的每一行。

阻礙

模糊比對會把一次猜錯變成一筆悄悄核准的付款。金額必須精確到分，而且一個帳號絕不能看到另一個帳號的發票。

行動

只做精確比對，金額從印出的字元直接解析成 Decimal。每個帳號會檢查兩次，一次在網頁層、一次在服務層，並有 132 項在真實 PostgreSQL 上執行的測試。

結果

20 個預設狀況全部如預期被找出，沒有多餘的發現；再次上傳同樣的 20 個檔案也沒有新增任何紀錄。第二個帳號要求讀取第一個帳號的檔案時遭到拒絕。

條件限制：一台電腦、合成的測試資料、沒有線上部署，還有一個可選的模型步驟（Claude，預設關閉），而它只讀過測試發票。

相近不代表相符，發票不會因此通過

決策

訂單與 SKU 只有完全相符或不相符兩種結果。PO-1007 寫成「PO 1007」時，會連同候選項一起回報，並等待人工處理。「無法讀取」是一個附帶原因的狀態，絕不是一張空白發票，而且無法讀取的檔案不能被核准。

捨棄了什麼

附分數的模糊比對被否決了。模型擷取也被延後：三個手寫範本就讀出了 18 份可讀測試檔的全部 144 個值，所以模型步驟是後來才加入、預設關閉，而且絕不會自行把一張發票標為無異常。

自己執行 invoice-check

只需要 uv，其他什麼都不用裝：沒有設定 DATABASE_URL 時，應用程式會自己啟動 PostgreSQL。示範腳本會用兩個拋棄式帳號，驅動執行中的伺服器走完整個流程，最後刪除這兩個帳號。

數字從哪裡來

docs/demo-run.txt，是 scripts/demo.py 對執行中伺服器跑出的輸出，包含帳號檢查。

閱讀 README 與完整結果

invoice-check / 終端機
$ uv sync
$ uv run uvicorn invoicecheck.app:app --port 8811  # open http://127.0.0.1:8811 and create an account
$ uv run python scripts/demo.py http://127.0.0.1:8811  # two throwaway accounts, deleted at the end
$ uv run pytest  # 132 tests, on a real PostgreSQL
